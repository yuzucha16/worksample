# 設計（design）— 固定長ブロックのメモリプール

状態: 判断 A〜E は **ユーザーが承認済み**（2026-10-06。`docs/decisions.md`）。「実装の初期値」（5 節）も **承認済み**（2026-10-06）。判断 F（Cortex-M0 の除算）は F4（M0 を対象外）で決定。実装は `src/pool.h` `src/pool.c`、テストは `tests/test_pool.c`。前提は、組込み領域（ユーザーは組込みエンジニア）、`docs/coding-rules.md` の制約（`src/` のみ: 動的確保なし、グローバル変数なし、初期値つき `.data` を減らす、再帰なし、libc 非依存）。

## 0. 設計の原則（ユーザーの方針。2026-10-06）

- **安全性を、起動速度より優先する**。安全性と起動速度を比べるなら、安全性を取る。起動速度に効く設計要素は、**チューニング要素**として、最初の設計の根拠にしない（後から測って調整する）。
- 実行時の不正の検出（二重解放など）より、**不正を起こさないことを、テストで確かめる**。呼び出し側の責務は、呼び出し側が果たす（復帰処理が難しいため）。

## 1. 要求（制約から導いたもの）

| 要求 | 出どころ |
|---|---|
| `malloc` を使わない。領域は呼び出し側が渡す | 動的確保の禁止 |
| ライブラリ内に状態を持たない（すべて構造体） | グローバル変数の禁止 |
| `.data` を増やさない。初期値は実行時に `pool_init` で設定する | 初期値つき `.data` の削減（フットプリント） |
| `alloc` と `free` が一定時間（O(1)）。断片化しない | 組込みの時間の決定性（固定長ブロックの利点） |
| ブロックごとのヘッダを持たない | フットプリント |
| libc に依存しない（`nm -u` が空） | 判断 C（承認） |
| 状態の不変条件が単純で、検査しやすい | 安全性の優先 |

## 2. API（`src/pool.h`）

```c
struct pool {              /* 呼び出し側が置く（スタック、または呼び出し側の static） */
  unsigned char *base;     /* ブロック領域の先頭（アライメント調整後） */
  size_t block_size;       /* 丸めた後のブロックサイズ */
  size_t capacity;         /* ブロック数 */
  void *free_head;         /* 空きブロックの単方向リスト */
};

enum pool_status { POOL_OK = 0, POOL_ERR_ARG, POOL_ERR_SIZE, POOL_ERR_PTR, POOL_ERR_CORRUPT };

enum pool_status pool_init(struct pool *p, void *buf, size_t buf_size,
                           size_t block_size, size_t align);
void *pool_alloc(struct pool *p);                   /* 空きが無ければ NULL */
enum pool_status pool_free(struct pool *p, void *block);
enum pool_status pool_check(const struct pool *p, size_t *free_count); /* O(n)。テスト・デバッグ用 */
```

- すべて `p` を引数で受ける。グローバルも `static` の状態も持たない。
- 失敗は、戻り値（`pool_status`）か `NULL`。`assert` と `abort` は使わない（libc 依存を避け、呼び出し側が処理を決める）。
- スレッド・割り込み: 再入しない。割り込みと共有するときは、呼び出し側が排他（割り込み禁止など）で囲む。この Project の範囲外（README）。ヘッダに明記する。
- `free_count` は `NULL` でもよい。テストが「すべて返却した」（`free_count == capacity`）を確かめるために使う。

## 3. メモリレイアウト

```
buf（呼び出し側）
 │ ← 先頭を align に切り上げる（切り捨てた分は使わない）
 ▼
 base ┌──────────┬──────────┬──────────┬─ ─ ─ ─┐
      │ block 0  │ block 1  │ block 2  │  ...  │  capacity 個、block_size ずつ隙間なし
      └──────────┴──────────┴──────────┴─ ─ ─ ─┘
 free_head → block 0 → block 1 → block 2 → … → NULL   （初期状態。すべて空き）
```

- **ブロックサイズ**: `block_size` を `max(要求, sizeof(void *))` にし、`align` の倍数に切り上げる。空きブロックは、先頭の `sizeof(void *)` バイトに、次の空きブロックへのポインタを置く（侵入型リスト）。使用中のブロックは、全体が利用者のもの。**ブロックごとのヘッダはなく、オーバーヘッドは 0**。
- **容量**: `capacity = (buf_size - 先頭の調整分) / block_size`。0 なら `POOL_ERR_SIZE`。
- **`pool_init`**（判断 A2）: 全ブロックを、アドレスの昇順に連結する（反復。再帰なし）。O(capacity) で、バッファ全体に書く。終了時、不変条件「空きリストが、全ブロックをちょうど1回ずつ含む」が成り立つ。
- **`pool_alloc`**: `free_head` を取り出す（`NULL` なら `NULL` を返す）。O(1)。
- **`pool_free`**: 範囲・整列を検査し（O(1)）、ブロックを `free_head` に積む（LIFO。O(1)）。`base` 未満、`base + capacity * block_size` 以上、または `base` からのオフセットが `block_size` の倍数でないときは `POOL_ERR_PTR`。
- **二重解放**（判断 B1）: 実行時には検出しない（O(1) では検出できない。検出しても復帰が難しいため、呼び出し側の責務）。テストで、「二重解放を起こさない」ことを確かめる（下の「テストの方針」）。`pool_check` は、テスト・デバッグ用に、リストの整合（範囲、整列、閉路なし、`free_count <= capacity`）を O(n) で検査する。壊れていれば `POOL_ERR_CORRUPT`。

### 判断のまとめ（承認済み）

| 判断 | 結果 | 理由（ユーザーの発言） |
|---|---|---|
| A 初期化 | **A2: 全ブロックを連結** | 安全性と起動速度を比べるなら、安全性を取る。この程度の設計要素はチューニング要素 |
| B 不正な `free` | **B1: O(1) の範囲・整列検査 + `pool_check`** | 二重解放をリアルタイム検知しても復帰処理が難しい。検知よりも、起こさないことをテストで見る。呼び出し側の責務 |
| C libc | **非依存（検査を `check-rules.sh` に実装済み）** | — |
| D ターゲット | **32bit MCU（Cortex-M 系など）** | 64bit（Cortex-A）は C++ と Linux 前提になり、コーディングで気にする領域が変わる。この Project の範囲外 |

### チューニング要素（後で測って判断する。いまは採用しない）

- 遅延切り出し（`pool_init` がバッファに書かず、未使用領域から必要になったときに切り出す）。起動時間は短くなるが、`alloc` の分岐と状態（`carved`）が増え、不変条件が複雑になる。起動時間が実測で問題になってから検討する。
- インデックス型のフリーリスト（`uint16_t` など）。最小ブロックサイズを `sizeof(void *)` より小さくできる。ブロックが小さい用途で、RAM が逼迫したときに検討する。

## 4. ターゲットの前提（判断 D）

- 主なターゲット: 32bit MCU（Cortex-M 系など）。`size_t` とポインタは4バイト、`max_align_t` は通常8バイト（ARM EABI）。**未確認**（ツールチェーンが無い。確認する案は 6 節）。
- ホスト（WSL の x86-64、64bit）でテストする。ポインタと `size_t` の幅に依存しない書き方にする（`uintptr_t` で計算し、幅を固定しない）。
- アライメントに厳しいコア（Cortex-M0 など。非整列アクセスでフォルトする）を想定し、`align` の検査（2のべき乗、`sizeof(void *)` 以上）と、返すブロックの整列の保証を、設計の一部にする。

## 5. 判断 E と実装の初期値

### 判断 E: strict aliasing（侵入型リストの設計上の論点）。**E1 を承認**（2026-10-06）

空きブロックの先頭に `void *` を書く。呼び出し側のバッファは `unsigned char` の配列（宣言された型）なので、規格上は、有効型（6.5 節）に反する書き込みになりうる。実務では広く使われるが、GCC は `-O2` の strict aliasing で、最適化により意図しない動作になる可能性がある。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **E1 `-fno-strict-aliasing` を `src/` のビルドに付ける（推奨）** | ビルド設定で回避。Linux カーネルなども採用 | 実装が素直。可搬 | 組込みの製品のビルド設定にも付ける必要がある（ビルドフラグの前提になる）。規格上の問題は残る |
| E2 `memcpy` で書く | 固定長（`sizeof(void *)`）の `memcpy` | 規格に沿う | libc 依存の検査（判断 C）と衝突しうる（`-O0` で呼び出しが残る）。`__builtin_memcpy` は GCC 拡張 |
| E3 `__attribute__((may_alias))` の型 | GCC 拡張で、エイリアスを許す型にする | 局所的 | 可搬でない（ARM Compiler など、ツールチェーンによる） |
| E4 そのまま | 何もしない | 最も単純 | `-O2` で壊れる可能性。テストは `-O1` なので、気づかない |

**E1 の実測**（確認: 2026-10-06、gcc 13.3、WSL、`tests/test_pool.c`）: `-fno-strict-aliasing` の有無、`-O1` `-O2` `-O3` のどれでもテストは通った。**この実装とテストでは、strict aliasing の問題は再現していない**。E1 は、再現できていない問題への予防（規格上の有効型の問題と、将来の最適化・コンパイラ更新への備え）として付けている。`Makefile` の `CFLAGS` に入っており、`test-o2`（`-O2`）でも同じテストを実行する。製品のビルドにも同じフラグが要る（ビルド設定の前提）。

### 実装の初期値（**承認済み**: 2026-10-06。`docs/coding-rules.md` の節 5 は、この節の要約）

- 型: サイズと個数は `size_t`、アドレスの計算は `uintptr_t`。ポインタ → 整数の変換だけを使い、整数 → ポインタは使わない（`buf + adjust` と配列添字で進める）。ユーザーの指示: ポインタ操作はコンパイラに任せる、明示的なポインタへのキャストは許容、整数演算の値をポインタとして扱わない。`void *` ↔ `void **` のキャストは、`node_set_next` `node_get_next` に閉じ込めた。**MISRA C への準拠は目標にしない**（ユーザーの指示）。
- 整数のオーバーフロー: ブロックサイズの切り上げと、アドレスの調整（`addr + mask`）は、オーバーフローを検査する。範囲の検査は、`capacity * block_size` の乗算を避け、除算で比べる（`offset / block_size >= capacity`）。
- 名前は `pool_` 接頭辞、`struct pool`（typedef なし。`_t` 終わりは POSIX が予約）。公開は `pool.h` だけ。内部は `static`。
- 反復だけを使う（再帰なし）。
- 失敗した `pool_init` は、`*p` を変更しない（テストで確認）。

### 判断 F: Cortex-M0 の除算。**F4（M0 を対象外にする）を承認**（2026-10-06。**この Project（`learn-c-pool-allocator-m0`、2026-10-07）で、M0 対応に置き換えた**。現在の設計は `docs/decisions.md` の「M0 の除算」。以下は前の Project の記録）

**結論**: 対象は、ハードウェア除算のある Cortex-M3 / M4 など。Cortex-M0 / M0+（ARMv6-M）は対象外。`src/pool.c` が、ARMv6-M でのコンパイルを `#error` で止める（対象外であることを、ビルドで強制する）。`make check-arm` は、M3 / M4 の未定義シンボルが無いことと、M0 が `#error` で止まることを確認する。M0 を使うことになったら、F1（2進の筆算。試作で 378 バイト、未定義シンボルなしを確認済み）で対応できる。以下は、判断の根拠（実測と選択肢）。

`pool_init`（`capacity = 残り / ブロックサイズ`）と `locate`（`offset / block_size`、`offset % block_size`）が、除算と剰余を使う。**Cortex-M0 / M0+ には除算命令が無い**ので、コンパイラが libgcc の補助関数を呼ぶ。

**実測（2026-10-06。ユーザーが `make check-arm` と `make size-arm` を実行。AI が試作とリンクで補った）**:

- 仮説は当たった。Cortex-M0 で未定義シンボル `__aeabi_uidiv` `__aeabi_uidivmod`。Cortex-M3 / M4 は OK（`make check` が、これを理由に、いま失敗する。意図した状態）。
- 容量（`.text` バイト。`.data` と `.bss` はすべて 0）:

| 案 | M0 | M3 / M4 | 未定義シンボル | 備考 |
|---|---|---|---|---|
| 現状（`/` と `%`） | 332 + libgcc 280 = **612** | **288** | M0 で出る | `__udivsi3` が 266 バイト |
| **F1 2進の筆算に置き換える（全コア共通）** | **378** | 358 | 出ない | 反復は `size_t` のビット数で打ち切り（一定時間）。M3/M4 では、ハードウェア除算より遅い（速度は未測定）。1 経路でテストしやすい |
| F2 `__ARM_FEATURE_IDIV` で切り替える | 378 | 288 | 出ない | M3/M4 は今のまま。M0 だけ筆算。経路が2つ（ホストのテストでは、筆算の経路を強制する設定が要る） |
| F3 libgcc を許可する（検査の対象から外す） | 612 | 288 | 許可リスト | コンパイラのランタイムは libc ではない、という整理。M0 の容量がほぼ2倍 |
| F4 M0 を対象外にする | — | 288 | 出ない | 今のまま。M0 を使う場合は、別の対処が要る |

F1 の試作（一時ディレクトリ）: ホストで `tests/test_pool.c` が、ASan・UBSan つき、`-O1` と `-O2` で通り、Cortex-M0 / M3 で未定義シンボルが無いことを確認した。`src/` にはまだ入れていない。

AI の推奨は F1 だった（原則「安全性を優先し、速度はチューニング要素」に合い、経路が1つ）。**ユーザーは F4 を選んだ**（M0 を使う予定がないため、と解釈。理由の発言は無い）。M0 が必要になったときの手がかりとして、F1 の試作の要点（`size_t` のビット数で打ち切る2進の筆算を `pool_init` の容量計算と `locate` に使う）を、この節に残す。

## 6. テストの方針（テストは実現のしやすさを優先。`tests/test_pool.c`。制約の対象外）

- バッファは、テストの関数内のスタック配列（`_Alignas(max_align_t) unsigned char buf[N]`）。ASan が、スタック配列の範囲外への書き込みを検出する（プールが `buf` の外に書かないことの検証になる）。
- **観点**:
  - 引数の検証（`NULL`、小さすぎるバッファ、不正な `align`）。
  - `pool_init` 直後に、`pool_check` が OK で、`free_count == capacity`（不変条件）。
  - すべてのブロックが整列していること、重ならないこと（個別のパターンを書いて検証）。
  - `capacity` 個を取ったあとの枯渇（`NULL`）、1つ返して取り直すと同じブロック（LIFO）。
  - 範囲外・非整列の `free`（`POOL_ERR_PTR`）。
  - リストを壊したときの `pool_check`（`POOL_ERR_CORRUPT`）。
  - **モデル検査**: 決定的な疑似乱数（固定シード）で、確保と解放を数千回繰り返し、テスト側のシャドウモデル（配列の使用中フラグ）と突き合わせる。**シャドウモデルで、二重解放を起こさないことを確かめる**（ユーザーの方針: 二重解放を、起こさないことで見る）。最後にすべて返却して、`free_count == capacity`。
- **フットプリント**: `make size` で、`src/*.o`（`-Os`、サニタイザなし、freestanding）の `.text` `.data` `.bss` を表示する。`.data` が 0 のことを目標にして記録する。**実測（ホスト x86-64、`-Os`。2026-10-06）: `.text` 633、`.data` 0、`.bss` 0（バイト）**。ARM 向けは `make size-arm`（Cortex-M0 / M3 / M4、`-mthumb -Os`）。`arm-none-eabi-gcc` は、dotfiles の `manifests/apt.txt` に追記済み（ユーザーの承認。実機への導入待ちで、いまは SKIP）。

## 7. 初期化の保証（2026-10-07。M0 の速度のチューニングで、`pool_alloc` と `pool_free` の検査を減らしたことに伴う設計。ユーザー承認）

`pool_alloc` と `pool_free` は、`struct pool` の中身を再検査しない。その代わり、構造体の状態を次の 2 つに限る（正本は `src/pool.h` の「初期化の保証」）。

- **(a) 全バイトが 0（未初期化）**: `pool_alloc` は `NULL`、`pool_free` と `pool_check` は `POOL_ERR_ARG`。`base == NULL` だけで判定する。
- **(b) `pool_init` が `POOL_OK` を返した後で、呼び出し側が書き換えていない**: 不変条件 I1〜I5 が成り立つ。I1 `base` が `align` の境界、I2 `block_size >= sizeof(void *)` で `align` の倍数、I3 `capacity >= 1` で `capacity * block_size` が `buf` に収まる、I4 `free_head` が空きリストの先頭、I5（除算なしの経路）`block_size = d * 2^shift`（`d` は奇数）で `inv * d = 1`。
- 失敗した `pool_init` は `*p` を変更しない。初期化していない自動変数に対する失敗した `pool_init` の後は、(a) でも (b) でもないので使えない（戻り値の確認は、呼び出し側の責務）。

保証の根拠は、実行時の検査でなく、テスト:

- 不変条件 I1〜I5 は、`pool_init` が成功した直後に、引数の組（要求サイズ 1〜90、`align` 8 / 16 / 32、先頭のずらし 0〜7）を総当たりして確かめる（`test_init_contract_sweep`、`check_contract`）。
- 失敗した `pool_init` が、全ゼロの構造体を全ゼロのまま残し、以後の操作で弾かれる（`test_failed_init_keeps_zeroed_pool_uninitialized`）。
- `pool_free` がブロックの先頭だけを受け付けることを、全バイトのオフセットで、除算と剰余による判定と突き合わせる（`test_free_accepts_exactly_block_starts`。要求サイズ 20 通りと `align` 組み合わせ）。
- ブロックの先頭の判定そのもの（乗法の逆元）は、`block_size` 1〜700、境界の `capacity`（`SIZE_MAX / block_size` を含む）で、約 5,400 万ケースを、参照の判定と突き合わせる（`tests/white_locate.c`。`pool.c` を直接取り込む。除算の経路と除算なしの経路の両方）。32 ビットは、ホストで直接は実行できない（`gcc -m32` が無い）ので、M0 の実バイナリを命令シミュレータで動かした確認（全バイトのオフセットで、13,392 ケース、不一致 0）で補った（一時の確認で、リポジトリには入れていない）。
- 変異テスト（一時の確認）: 判定の境界の誤り、シフトの誤り、逆元の反復不足、`shift` の未設定、`free_head`、リスト終端、`capacity` の数え間違い、`is_initialized` と `pool_check` の検査の欠落を、それぞれ入れて、テストが失敗する（検出される）ことを確かめた。
- `pool_check`（debug 用）は、(a)、`block_size < sizeof(void *)`、`capacity == 0` を `POOL_ERR_ARG` にする（以前の `is_initialized` と同じ範囲）。I5 は、フットプリントのため検査しない（検査を足すと `.text` が 36 バイト増える）。
