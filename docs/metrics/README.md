# interview・改善提案の指標（metrics）

AI がユーザーに聞く質問と、AI が出す提案（承認の確認、改善フックの改善案）の効果を測るデータ。最終的に、AI が提案・回答をループして質問と提案を改善するための入力にする。この指標自体も改善の対象にする（ユーザーの指示）。判断は `docs/decisions.md`（「開始インタビューの指標を、1質問1行のイベントログで集める」）。

- 正本は `events.csv`（1質問・1提案につき1行。追記する）。集計は `summarize.ps1`（全体・Area・Project・出どころ・セッションの単位。`kind` ごとに出す）。
- **記録する人**: AI（エージェント）。ユーザーの回答を受けた同じターンで行を足し、セッションの終わり（終了処理）に、`reversed`（後で覆ったか）と `adopted` の確定を埋める。ユーザーに記録の作業は求めない。
- **セッション**: 開始インタビューから終了処理までの区間（会話の単位ではない）。ID は `<日付>-s<連番>`。
- このリポジトリ（PC ごと）で閉じる。PC1 と PC2 は別インスタンスで、集計も別。共有側（`resources/`）には、一般化した結論だけを渡す（ナレッジ化）。

## 列

| 列 | 内容 |
|---|---|
| `date` | 日付（YYYY-MM-DD） |
| `session` | セッション ID。`<日付>-s<連番>`（同じ日の会話ごとに増やす） |
| `area` `project` | 所属。該当なしは `-`（`works` 全体の検討など） |
| `work_type` | 作業の種類。自由記述から始め、安定したら語彙を固定する（文書作成: 仕様・設計・調査、開発: 設計・実装・評価 など。抽象化・継承の候補） |
| `kind` | `interview`（聞き取り）、`approval`（AI の提案・解釈への承認の確認）、`improvement`（改善フックの改善案）、`gap`（質問が漏れていた: 聞かれなかった前提を、ユーザーが後から足した。件数だけを見る。率は意味を持たない）。集計は別々に出す |
| `q_id` | 識別子（質問は `<session>-q<連番>`、改善案は `<session>-i<連番>`、取り込みは `<日付>-imp<連番>`）。質問の版を変えたら別の ID にする |
| `question` | 質問・提案の要旨（短く） |
| `source` | 質問: `template`（手順書の定型）、`adhoc`（その場で作った）、`prompt`（ユーザーがプロンプトで渡した）。改善案: `hook`（フックの実行後の提案）、`prompt`（ユーザーの指示・指摘。AI の提案ではない） |
| `format` | `choice`（選択・承認）か `free`（自由記述） |
| `answered` | 1 = 回答・承認・却下のどれかがあった、0 = スキップ・無視・保留（`提案` のまま） |
| `adopted` | 1 = 回答が成果物（決定、README、ゴールの要約）に反映された、0 = 反映されない、空 = 未確定 |
| `fix` | 1 = ユーザーが質問の前提・選択肢・提案の内容を直した（ズレていた）。空 = 未判定（適合率の母数に入れない） |
| `supplement` | 1 = 質問・提案の範囲を超えて、ユーザーが情報を足した |
| `answerable` | 1 = 答えが既に `docs/` やファイル、環境の確認で分かり、聞かなくてよかった（改善案では、既存の規則で足りていた）。空 = 未判定 |
| `reversed` | 1 = 採用後に撤回・変更された、0 = 確認期間を過ぎても維持、空 = 未確定 |
| `basis` | `live`（回答を受けた同じターンで記録）、`backfill`（後から会話を見て推定して起こした。精度が落ちる）、`import`（既存の表の状態列から機械的に取り込んだ。`fix` `supplement` `answerable` は空） |

| `cause` | 補正（`fix` `supplement` `gap`）の起因。`ai`（AI の質問・提案の欠陥）、`user`（ユーザーの指示不足）、`review`（ユーザーの批判的レビューの成果）。補正が無い行は空。2026-10-06 に追加（以前の行は空 = 未判定） |

## 指標の定義

| 指標 | 式 | 読み方 |
|---|---|---|
| 質問数（母数） | 行数 | |
| 回答率 | 回答数 / 質問数 | 低い = 聞く価値が低いか、答えにくい |
| 採用率 | 採用数 / 回答数 | 低い = 聞いても使わなかった。質問の削減候補 |
| 適合率 | （回答数 − `fix` か `supplement` のある回答数）/ 回答数 | 低い = 質問がズレている、または粒度が足りない |
| 修正数・補足数 | `fix` と `supplement` の件数 | 修正は質問の欠陥、補足は質問の不足 |
| 冗長率（推奨） | `answerable` / 質問数 | 高い = 事前に `docs/` を読めば聞かずに済む |
| 覆り率（推奨） | `reversed=1` / （`reversed` が確定した行） | 高い = 採用が早すぎた、または質問が結論を誘導した |

推奨する追加の指標（AI の提案。未承認の項目は試行で採否を決める）:

- **漏れ（`gap`）**（2026-10-06 に追加。ユーザーが承認した形式の拡張）: 聞かれなかった前提が後から出た件数。適合率（聞いた質問のズレ）と違い、聞かなかった質問の欠落を測る。同じ種類の漏れが繰り返されたら、インタビューの項目に足す根拠になる（例: 専門領域、コーディングルール）。

- 冗長率と覆り率（上の表。列は用意済み）。
- セッションの達成度: 終了処理で、開始時のゴールが達成されたか（達成・一部・未達）。質問の効果を、最終的な結果につなげる。**列は未用意**（セッションの単位の表が要るため、必要になったら `session-outcomes.csv` を足す）。
- 質問数・所要ターン数 / セッション: 重さ。小さな再開で1問に縮める設計の判断に使う。
- 質問の出どころ別（`source`）の採用率: 定型の質問が育っているか。
- 作業の種類（`work_type`）別の集計: 種類ごとの共通部分と差分を見つける（定型化の入力）。

## 改善フックへの適用

改善フック（kit の `knowledge-hook.md`「このフックの改善」と、それを使う `closing-hook.md` `integrate-hook.md` `setup-hook.md`）の改善案も、同じ列で記録する（`kind=improvement`）。承認制の流れ（提案 → ユーザーの承認・却下・修正 → `improvements.md`）が、質問の流れと同じ形のため。

- 1案 = 1行。`answered` は承認・却下のどちらかがあったか。`adopted` は採用。`fix` は、ユーザーが案を直して採用したか。
- `improvements.md` の既存の66件は、`import` で取り込んだ（状態列だけから。取り込みは一度きり。以後は `live`）。
- **自動採用の行（2026-10-08 から。試験運用）**: `wrap` の「自動採用の規則」は、承認を取らないので、`answered=0`、`adopted=1`、`basis` に `live;auto` と書く。承認の指標（回答率、採用率、`fix`）には含めず、集計では分けて読む（`summarize.ps1` は、まだ分けていない。`basis` に `auto` を含む行を除いて読む）。`reversed` は、`review` が削除・復活したときに確定する（削除 = 1）。
- 見直しの指標は、`reviews.csv`（1回の `review` につき1行。列と読み方は kit の `review-hook.md`）と `rule-hits.csv`（自動採用の規則が働いた記録。`wrap` が足す）。**削除率は単独で見ず、再発率と規則の総量（`rules_chars`）と組で見る**。
- 取り込みで分かったこと（2026-10-06）: 採用率が約98%で、判別力が低い（却下は撤回を除いて0件）。承認が形式になっていないか、提案が事前に絞られているかは、このデータからは分からない。**採用率より、`fix`（直されたか）と `reversed`（後で覆ったか）を `live` で取る方が、改善案の質を測れる**。

## スレッドとセッションの指標（AI 活用・workflow の効果。2026-10-06 に追加）

目的は、自己改善（ユーザー本人のみ。第三者への評価には使わない。ユーザーの指示）。忖度のない評価にするため、観測できる行動と件数だけを取り、各行に根拠を残す。

- **用語**: スレッド = Claude Code の1会話（jsonl 1本）。セッション = 開始インタビューから終了処理まで（既存の定義）。1スレッドに複数セッション、複数スレッドで1セッションがありうる。紐づけは `sessions.csv` の `thread_id`。
- **`threads.csv`**（自動。`extract-threads.ps1` が jsonl から書く。派生データで、履歴が消えても既存の行は残す）: 1スレッド1行。
  - 自走: `prompts`（実プロンプト数）、`turn_med_s` `turn_p90_s` `turn_max_s`（ターン = 実プロンプトから次の実プロンプトの直前まで。30分で打ち切り）、`capped_turns`（打ち切った数。離席・許可待ち・放置の混入）、`tools_total` `tools_per_turn_med`、`active_min`（打ち切り後のターン長の合計。壁時計ではない）。
  - 無駄の合図: `tool_errors`（ツールエラー数。無駄な試行の代理）、`out_tokens` `fresh_in_tokens` `cache_read_tokens`（トークン）、`ctx_max_tokens`（1回の入力の最大。コンテキスト量の代理）。
- **`sessions.csv`**（AI が終了処理で1行足す）: `session` `date` `thread_id`（`extract-threads.ps1 -Current` の値）`area` `project` `work_type`、`outcome`（達成・一部・未達。開始時のゴールとの突き合わせ）、`prompt_complete`（最初の依頼に、ゴール・完了条件・制約・やらないことが入っていた数 0〜4）、`prompt_evidence`（その根拠。ユーザーの発言の要旨）、`review`（ユーザーが AI の出力を批判・修正した件数。`events.csv` の `cause=review` と対応）、`mechanism`（ルール・フック・記憶に落とした件数）、`note`（無駄の所見）、`start_mode`（開始の形。`bare` = 「作業を始めて」だけで始めた、`briefed` = 最初の依頼にゴール・完了条件・制約・やらないことを添えた。開始インタビューの効果と、最初の依頼の完備度を、別々に比べるため。2026-10-06 に追加）。
- **無駄の見方**: `extract-threads.ps1 -Report`。「セッションに紐づかない」「放置（既定3日）」「ツールエラー率20%以上」「打ち切りターンあり」を合図として出す。合図は判定ではなく、中身を見て決める。トークン単価（成果1件あたり）は、`outcome` と紐づいてから見る。
- **自走時間を伸ばす目的の注意**: 単独で目標にしない。品質（`fix` `gap` `reversed` `outcome`）と対で見る。`work_type` を分けて比べる。
- 制約: 履歴に compact の記録が見当たらない（未観測）ので、コンテキスト量は `ctx_max_tokens` で代用する。Claude Code は古い履歴を消すことがあるので、定期的に `extract-threads.ps1` を回す（終了処理で回す）。

## 制約

- 母数が小さいうちは、率より件数と中身を見る（1つの質問で1行でも、率は 0 か 100% になる）。
- `backfill` の行は、`live` と分けて読む。
- 質問と提案の文面は、機密・個人情報を含めない（`question` は要旨だけ）。
