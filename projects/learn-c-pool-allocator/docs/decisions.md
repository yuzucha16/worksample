## Principles

- 【汎用】安全性を、起動速度より優先する。起動速度に効く設計要素は、チューニング要素として扱い、最初の設計の根拠にしない（後から測って調整する）。（ユーザーの方針。2026-10-06） 行き先: 未仕分け
- 【汎用】実行時の不正の検出（二重解放など）より、不正を起こさないことをテストで確かめる。呼び出し側の責務は、呼び出し側が果たす。理由: 実行時に検知しても、復帰処理が難しい。（ユーザーの方針。2026-10-06） 行き先: 未仕分け

## Decisions

### 【この件】メモリプールの設計の判断 A〜D（2026-10-06。ユーザーが承認。設計は `docs/design.md`）

- 決めたこと:
  - A 初期化: **全ブロックを連結する**（`pool_init` が O(capacity) でバッファ全体に書く）。遅延切り出しは採らない。
  - B 不正な `free`: **O(1) の範囲・整列の検査だけ**にし、二重解放は `pool_check`（テスト・デバッグ用）で見る。実行時には検出しない。
  - C libc: **`src/` は libc に依存しない**。検査を `tools/check-rules.sh` に足した（`-ffreestanding` で `-O0` と `-Os`、未定義シンボルが無いこと）。
  - D ターゲット: **32bit MCU（Cortex-M 系など）**。64bit（Cortex-A）は、C++ と Linux 前提になりコーディングで気にする領域が変わるので、この Project の範囲外。
- 根拠（ユーザーの発言）: A: 安全性と起動速度を比べるなら、安全性を取る。この程度の設計要素はチューニング要素。B: 二重解放をリアルタイムに検知しても復帰処理が難しい。検知よりも、起こさないことをテストで見る。呼び出し側の責務。D: Cortex-A なら C ではなく C++ と Linux 前提。
- 修正された AI の前提: 設計の根拠に「起動を楽にする」を使ったのは、AI が、「初期値つき `.data` を減らす」というユーザーの目的を、設計全体に広げた拡大解釈だった。ユーザーが、その記述の削除を指示した（`docs/design.md` から削除した。チューニング要素の節に移した）。
- 却下案（ユーザーの選択）: A1 遅延切り出し（推奨案だった。チューニング要素として後で検討）。B2 常時の二重解放検出、B3 ビットマップ。
- 確認済み: `make check` が通った（libc 依存の検査を含む。2026-10-06）。`-Os` では `memset` が最適化で展開され、`strlen` だけが残る。`-O0` では両方が出る（両方の最適化レベルで見る理由）。
- 行き先: local（この Project の設計）

### 【この件】ビルド環境は WSL（Ubuntu 24.04）の gcc と make にする（2026-10-06。ユーザーが承認）

- 決めたこと: コンパイルとテストは WSL の gcc 13.3.0 と make で行う。サニタイザ（AddressSanitizer、UndefinedBehaviorSanitizer）は gcc のものを使う。
- 根拠: Windows 側に `gcc` `clang` `cl` `cmake` `make` が無く、WSL には `gcc` と `make` がある（確認: 2026-10-06、根拠: `Get-Command` と `wsl` での `command -v`。`clang` `cmake` `gdb` `valgrind` は WSL にも無い）。追加の導入なしで、完了条件（ASan・UBSan の警告 0）に届く。
- 却下案: Windows 側のコンパイラの導入（WSL で足りる）。WSL に `clang` や `gdb` を先に導入する（このセッションのゴールが増える）。
- 補足（ユーザーの方針）: WSL の環境は暫定で作ったもので、テストや自動化のためのツールが必要になれば、dotfiles に追記して育てる。kit は、これが PoC 相当なので、このセッションでは変更しない。
- 行き先: local（この Project のビルド環境）

### 【この件】判断 E: `src/` のビルドに `-fno-strict-aliasing` を付ける（E1）。ARM のツールチェーンを入れる（2026-10-06。ユーザーが承認）

- 決めたこと: 侵入型の空きリスト（空きブロックの先頭に `void *` を書く）のため、`src/` のビルドに `-fno-strict-aliasing` を付ける（`Makefile` の `CFLAGS`、`make size` と `check-arm` のフラグ）。`gcc-arm-none-eabi` を dotfiles の `manifests/apt.txt` に追記する（Cortex-M 向けのフットプリントと、libc 非依存の検査のため）。
- 根拠: 呼び出し側の `unsigned char` 配列に `void *` を書くのは、規格上の有効型の問題がある。`-O2` 以降の最適化で意図しない動作になる可能性がある。E1 は、実装が素直で、Linux カーネルなども採用している。
- 却下案: E2 `memcpy`（libc 非依存の検査と衝突しうる）、E3 `may_alias`（可搬性が低い）、E4 何もしない。
- 確認済み（2026-10-06、gcc 13.3、WSL）: `-fno-strict-aliasing` の有無、`-O1` `-O2` `-O3` のどれでも、`tests/test_pool.c` は通った。**問題は再現していない**ので、E1 は予防の位置づけ。製品のビルドにも同じフラグが要る（ビルド設定の前提）。
- 行き先: local（この Project の設計）

### 【この件】コーディングルール、制約、チェックを定める（2026-10-06。ユーザーが承認。暫定）

- 決めたこと:
  - 書式: 既存コードの書式（2スペース、80桁、コメントは日本語、`snake_case`）を規則にする。改行コードと文字コードを規則に加える（ユーザーの指示。値の LF と UTF-8（BOM なし）は、リポジトリの `.gitattributes` に合わせて AI が補った）。
  - 制約（ユーザーの指示。暫定）: グローバル変数の禁止、`.data` の使用をできるだけ抑える、再帰の禁止、動的確保の禁止。
  - チェック: 追加の警告フラグと `-fanalyzer` を Makefile に入れる。`clang-format` を導入する（理由: 一貫性のためでなく、コードリーディングのコストを下げるため）。`cppcheck` と `clang-tidy` は導入しない。
- 根拠: 実装前に規則とチェックを置くと、警告を最初から潰せる。制約は機械で検査できるものを `tools/check-rules.sh` にした（`make probe` で、違反が検出されることを確認した）。
- 却下案（ユーザーの選択）: 「ツールは今は導入しない」（推奨案）。`cppcheck` と `clang-tidy` の導入（今回は見送り）。
- 確認で修正された点（2026-10-06。ユーザーの回答。AI の解釈を直した）: ① 制約の適用範囲は `src/` のみ。ユーザーは組込み領域のエンジニアで、制約は組込み用途のため。テストコードは実現のしやすさを優先する。② 「`.data` を抑える」の目的は、初期値つき `.data` を減らして、フットプリントの削減と起動を楽にすること。`.bss` は、グローバルでなければ許可。当初の AI の読み（`.data` と `.bss` の全変数を禁止）は強すぎた。`tools/check-rules.sh` を、初期値つき `.data`（`D` `d`）とグローバル変数（外部リンケージの `B` `C` `G` `S`）の禁止に直し、許可される例（`static const`、グローバルでないゼロ初期化の `.bss`）を通す対照を足した（確認: 2026-10-06、`make check` が通った）。
- 後日の修正（2026-10-06。ユーザーの指示）: 上の ② の「起動を楽にする」の記述を、`docs/coding-rules.md` の `.data` の制約から削除した（目的はフットプリントの削減だけ）。この項目の記述は、ユーザーが当時に述べた回答の記録なので、そのまま残す。
- 未解決: 再帰の禁止は検査していない（`docs/coding-rules.md` の「未検査」）。ファイルスコープの `static`（ゼロ初期化）は、`nm` で関数内の `static` と区別できず、許可になる（限界。レビューで見る）。
- `clang-format` は導入済み（`clang-format 18.1.3`、ユーザーの報告）。最初の `make check` で、手で揃えたマクロの `\` を指摘し、`make format` で直した。
- 行き先: local（この Project の規則）

## Facts

- 【汎用】サニタイザが実際に効いていることは、意図したバグ（ヒープの範囲外書き込み、符号付き整数のオーバーフロー）を含む小さなプログラムで、検出されて非ゼロで終わることを確認できる。`make probe` で、ASan と UBSan の両方が検出した（確認: 2026-10-06、gcc 13.3.0、WSL。`-fno-sanitize-recover=undefined` を付けないと、UBSan は警告を出して終了コード 0 で続行する。サニタイザなしも 0。対照で確認: 2026-10-06）。 行き先: 未仕分け

## Gotchas

- 状況: UBSan のプローブが、検出されなくても `make probe` で「検出した」と判定された（`OK: UBSan が検出した`）。
  - 原因: プローブの `main` が、オーバーフローした値で終了コードを決めていて（`x == 0 ? 0 : 1`）、検出の有無と無関係に非ゼロで終わった。
  - 解決: 通常は終了コード 0 で終わる形にし、サニタイザなし・`recover` 許可（どちらも 0）と、`-fno-sanitize-recover=undefined`（非ゼロ）を対照して確認した（2026-10-06）。
  - 【汎用】行き先: 未仕分け
