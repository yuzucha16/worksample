- **速度のチューニングの見積もり（提案。未承認・未実装）**。測り方: コンパイル済みの `pool.o` を、Cortex-M0 の Thumb-1 の最小シミュレータ（一時ディレクトリ。TRM のサイクル表、ウェイト 0。未知の命令は即停止）で実行した。実機・QEMU は無い（WSL に無く、unicorn も入らなかった）。動作は、確保順、解放の成否、`pool_check` の個数、途中のポインタの拒否で合っていることを、実行のたびに確かめた。64 ブロック、`block_size` 8〜104。
  - 現状の主な遅さ: `pool_free` が 532 サイクルで、`pool_alloc`（41）の約 13 倍。原因は、`locate` の境界検査（ビットごとの剰余。32 回転）。`pool_check` は、64 ブロックで 31,926（ノードごとに `locate`）。`pool_init` は 1,299（ブロック当たり約 20）。
  - 案（すべて M0 の経路（`POOL_SOFT_DIV`）の中だけ。M3 / M4 は変更なし）:
    - **S1 乗法の逆元で境界検査**: `block_size = d・2^k`（`d` は奇数）として、offset が倍数であることを、下位 k ビットが 0 かつ `(offset >> k) * inv(d) < capacity` で判定する（範囲検査も兼ねる。逆元はニュートン法で、乗算だけ）。
    - **S2 初期化ループの統合**: 個数を数えるループと連結ループを 1 つにし、ループ本体も短くする。
    - **S3 `is_initialized` を縮める**（`p != NULL && p->base != NULL`）: `pool_alloc` の呼び出しコストが減る。
    - **S4 逆元と k を構造体に持つ**（RAM が 1 プールにつき 8 バイト増える）: `pool_free` から、逆元の計算を除く。

  - **乗算が遅い M0 では、見積もりが変わる**（Cortex-M0 は、乗算 1 サイクルが既定で、32 サイクルの小型乗算器の選択肢がある。対象のマイコンは未確認）。32 サイクルにすると: 現状の free 563 → S1+S2 は 442（−21% だけ）、S1+S2+S3 は 422、S4 は 103（−82%）。S4 は、乗算が 1 回なので、乗算の速さにほとんど依らない（init は逆元の計算が残るので 1,102）。
  - 検証: S1 の判定は、`offset / bsize < capacity && offset % bsize == 0` と、32 / 64 ビットのそれぞれ約 8,160 万ケースで不一致 0（`block_size` 1〜700、`capacity` の境界値、ランダムな offset）。S1+S2 と S1+S2+S3 の構成は、リポジトリの `make test-soft` `test-soft-o2` が通る（試作を一時コピーで実行。リポジトリのコードは変更していない）。
  - リスク: ① S3 で `block_size` と `capacity` の検査が無くなっても、既存のテストが通る（これらの検査を確かめるテストが無い）。S3 を取り込むなら、先にテストを足す。② S1 は `block_size` が 0 だと、k を求めるループが止まらない。`is_initialized` の `block_size >= sizeof(void *)` が防いでいるので、S3 と S1 の組み合わせでは、構造体が壊れたときに、エラーでなく無限ループになる。S3 の縮め方は、`block_size` の検査を残す形にする。③ S4 は構造体の大きさが変わるので、`pool.h` を、呼び出し側のすべてが同じ条件でコンパイルすることが必須（条件が食い違うと、構造体の配置が合わない）。④ 速度は、シミュレータの値（実機の確認は無い）。分岐やフラッシュのウェイトで、実機は遅くなる（比は大きくは変わらない見込み）。
